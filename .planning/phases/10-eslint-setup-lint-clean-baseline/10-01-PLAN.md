<objective>
Install ESLint 10 for the first time on this codebase (zero prior lint tooling) and wire the minimal working flat config: `@next/eslint-plugin-next`'s `configs['core-web-vitals']` export used directly (NOT `eslint-config-next`), plus a `@babel/eslint-parser`-based parser block for `.ts`/`.tsx` syntax parsing, plus `npm run lint`/`npm run lint:fix` scripts. This is the foundation every later plan in this phase extends -- `eslint.config.mjs` and `package.json` are both touched again in Plans 02/03, so this plan must land first (Wave 1).

Purpose: Next.js 16 removed `next lint` entirely (confirmed via official docs, research/STACK.md Question 1) -- there is no fallback CLI, so ESLint must be installed and invoked directly. A first pass at this phase discovered that `eslint-config-next` (both its `core-web-vitals` AND `typescript` sub-exports) crashes at require-time (`Cannot read properties of undefined (reading 'Cjs')`) against this project's locked `typescript@7.0.2` (tsgo) -- confirmed via direct `require()` of both `dist/core-web-vitals.js` and `dist/typescript.js` -- because it transitively depends on `typescript-eslint`, and no published `typescript-eslint` version (including `canary`) supports TypeScript >=6.1 as of this research. The user chose to bypass this by using `@next/eslint-plugin-next` directly (confirmed via live `require()` this session: it depends only on `fast-glob`, zero TypeScript-package dependency) and parsing `.ts`/`.tsx` via Babel's syntax-only parser instead of `@typescript-eslint/parser`. Shipping two milestones with zero lint tooling is, per research/FEATURES.md, "the single most visible gap an interviewer would find in 10 seconds of opening package.json."
Output: `eslint@10.7.0`, `@next/eslint-plugin-next@16.2.10`, `@babel/core@8.0.1`, `@babel/eslint-parser@8.0.1`, `@babel/preset-typescript@8.0.1`, `@babel/preset-react@8.0.1` installed; `eslint.config.mjs` created; `npm run lint`/`npm run lint:fix` scripts wired.
</objective>
