<objective>
Reach the lint-clean baseline this phase's ROADMAP success criteria require: a reviewed two-pass `eslint --fix` (non-domain broad, `src/domain/` reviewed line-by-line), then `eslint --fix --suppress-all` to absorb whatever remains into a tracked `eslint-suppressions.json` -- never by disabling or downgrading a rule. Document, rather than attempt, the fact that no type-checked ESLint tier exists at all in this toolchain (LINT-02's `recommended-type-checked` stretch goal is now technically impossible, not just noisy -- see below). Close with two small, cheap polish items already scoped into this milestone's research: a repo-root `.editorconfig` and a README "Linting & Code Quality" section.

Purpose: introducing a linter to an already-built codebase and leaving it red, or leaving it green only because rules were quietly turned off, is worse than not having one (research/FEATURES.md, research/PITFALLS.md Pitfall 1). This plan is what actually earns the "lint-clean baseline" claim in the phase's ROADMAP goal. Separately, this phase's toolchain (`@next/eslint-plugin-next` + `@babel/eslint-parser`, per research/STACK.md's CORRECTION) has zero TypeScript-aware parser in the mix by design -- there is no `recommended-type-checked` upgrade path to attempt, since that requires `typescript-eslint`, which crashes at require-time against this project's locked `typescript@7.0.2` (tsgo). This must be documented as a deliberate, known limitation rather than quietly dropped, so the gap between "lint-clean" and "type-aware-lint-clean" stays visible to a future reader of this repo.
Output: `npm run lint` exits 0; `eslint-suppressions.json` committed; `src/domain/` diff reviewed and full test suite green; the missing type-checked tier documented in README.md and SUMMARY.md as a known limitation; `.editorconfig` and README section added.
</objective>
