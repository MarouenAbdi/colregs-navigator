<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scenario-service.ts -> Postgres (via repository) | Vessel data reconstructed from stored rows re-enters domain logic (`classifyEncounter`) on every read |
| createScenario input -> persisted row | Vessel data has already passed Zod validation upstream (Plan 03's router), but this is the last point before a row becomes permanently persisted |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-03 | Tampering | scenario-repository.ts (all Prisma queries) | mitigate | All queries go through Prisma Client's generated, parameterized methods (`prisma.scenario.create`/`findUnique`/`findMany`/`update`) -- no `$queryRawUnsafe` or string-concatenated SQL anywhere in this file, per RESEARCH.md's Anti-Patterns |
| T-3-04 | Tampering | scenario-service.ts `createScenario` | mitigate | Genuinely un-classifiable input (e.g. coincident positions, which `VesselSchema`/`PositionSchema` do not forbid) is rejected with `BAD_REQUEST` before persistence, via a `classifyEncounter()` dry-run validation call -- prevents a degenerate row from ever being written, which is the root cause RESEARCH.md's Pitfall 3 warns about |
| T-3-05 | Information Disclosure | scenario-service.ts defensive `!result.ok` branch in getScenario/listGallery | accept | This branch is theoretically unreachable given T-3-04's create-time validation; it throws a generic `INTERNAL_SERVER_ERROR` rather than leaking the internal `DegenerateCaseReason`/`details` to the caller, consistent with not exposing domain-internal `Result<T>` shapes across the application-layer boundary (D-10) |
</threat_model>
