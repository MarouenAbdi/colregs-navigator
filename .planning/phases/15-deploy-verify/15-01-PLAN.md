    slow-but-successful Neon cold-start wake must still resolve to 200). Do not add app
    version/uptime/commit metadata to either response body (D-05). Do not build a generic

    DB-ping utility -- inline the query and both branches directly in this ~15-line file

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-15-01 | Information Disclosure | `GET /api/health` catch branch | mitigate | Discard the caught error entirely; body is a hardcoded literal `{status:"error"}`, never an interpolated error/stack/connection string (D-06); acceptance criteria grep the 503 body for absence of `postgresql://`/stack-trace substrings |
| T-15-02 | Tampering (false-confidence caching) | `GET /api/health` response caching | mitigate | `dynamic = "force-dynamic"` + explicit `Cache-Control: no-store` header on both branches (D-08), so an edge/browser cache can never mask a real DB outage behind a stale 200 |
| T-15-03 | Denial of Service (resource exhaustion via an unauthenticated endpoint) | `GET /api/health` | accept | A single `SELECT 1` per request against Neon's already-provisioned compute is negligible cost at this portfolio project's traffic scale; ASVS L1 does not require rate-limiting for a health check endpoint at this size, and D-05/D-06 already keep the endpoint minimal (no expensive queries, no auth surface to attack) |
