<objective>
Verify HEALTH-03: that the live production deployment survives a request issued after a
genuine, multi-hour (8+ hour) period of zero traffic -- the one requirement in Phase 15 that
cannot be satisfied synchronously within a single execution pass, because it requires a real
wall-clock wait, not a simulated or short-circuited one.

Purpose: RESEARCH.md's Pitfall 7 is explicit that Neon's free-tier compute already
auto-suspends after 5 minutes of inactivity (not configurable) -- so the DB has been
suspended for hours before "overnight" is even reached. The only thing an idle check can
actually prove is that a single request after a genuine multi-hour gap still succeeds
(elevated latency expected and fine), and that the check itself was not run too soon after
the last real traffic (which would produce a false pass proving nothing about a genuine
cold path). Plan 15-04's rollback/promote exercise is itself live traffic against the
production app, so the idle window this plan measures must start only after that traffic
has fully settled -- not overlap with it.

Output: A confirmed HEALTH-03 result (real curl status/latency after a genuine >=8h idle
window) and an updated `README.md` Deployment section recording that real result.
</objective>
