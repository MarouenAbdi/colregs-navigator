Empirically confirmed build-time DB dependency (read directly from
src/components/gallery/GalleryContainer.tsx): it is an `async` Server Component (no
`"use client"`) that calls `getCaller().gallery.list()` directly against Prisma at render
time, and no file in `app/` or `src/components/gallery/` sets
`export const dynamic = "force-dynamic"` or otherwise opts the "/" route out of static
generation. This means **the `build` job needs a real, migrated, reachable Postgres instance
-- not just the `test` job** -- or `next build --webpack`'s static generation of `/` will
throw trying to reach a nonexistent database. An empty (unseeded) table is fine; an
unreachable one is not.

prisma.config.ts calls `env("DATABASE_URL")` at config-load time. This threw in Prisma <7.2.0
even for non-connecting commands like `generate`; this project is locked to `^7.8.0`
(comfortably past the fix per prisma/prisma#28869/#28590/#28708, cited in
research/ARCHITECTURE.md), so `prisma generate` should succeed with no DATABASE_URL set at
all -- but set a placeholder value anyway in the lint/typecheck jobs as zero-cost
defense-in-depth (ARCHITECTURE.md's explicit recommendation).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| PR-supplied code -> GitHub Actions runner | `pull_request`-triggered jobs execute code/config from the PR branch on a shared-infrastructure runner |
| CI workflow -> ephemeral Postgres container | Non-secret, disposable dev credentials, scoped to one workflow run |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-01 | Tampering | `.github/workflows/ci.yml` default token scope | mitigate | Top-level `permissions: contents: read` -- no write scope available to any PR-triggered run regardless of PR content |
| T-14-02 | Information Disclosure | `DATABASE_URL` values embedded in workflow YAML | accept | Only the already-public local dev credentials (`colregs`/`colregs`, already committed in `.env.example`/`docker-compose.yml`) ever appear here; no GitHub Secret is created or referenced by this workflow |
| T-14-03 | Tampering (supply chain) | `actions/checkout@v7`, `actions/setup-node@v7` | accept | First-party GitHub Actions org, pinned to major-version tags (`v7.0.1`/`v7.0.0` confirmed live at planning time); acceptable at this project's scale, revisit with full-SHA pinning if this becomes a multi-contributor repo |
| T-14-04 | Denial of Service | Unbounded CI runs triggered by repeated pushes/PRs | accept | Solo-maintained portfolio repo, low-value target; GitHub Actions' account-level minutes cap is the natural backstop |
</threat_model>
