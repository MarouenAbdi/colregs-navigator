# Milestone v1.0: COLREGS Navigator

**Status:** ✅ SHIPPED 2026-07-18
**Phases:** 1-5
**Total Plans:** 19

## Overview

Built COLREGS Navigator as a stack of horizontal technical layers, assembled bottom-up: the pure domain layer (geometry primitives, then the COLREGS rules engine) was built and fixture-tested in complete isolation first, since it was both the highest-risk-of-subtle-bugs work and the entire portfolio-value proposition of the project. Only once the domain layer was proven correct did the roadmap move to the persistence/API layer (Prisma + tRPC), then the interactive SVG chart sandbox (wired directly to the already-correct domain layer for live drag classification), and finally save/share and the curated gallery — which reused the persistence layer and sandbox UI built in the prior two phases rather than introducing new architecture. Nothing was demoable end-to-end until Phase 4; that tradeoff was deliberate (Horizontal Layers mode), validating the riskiest logic (COLREGS classification) before any UI or persistence complexity sat on top of it.

## Phases

### Phase 1: Domain Foundations

**Goal**: The domain has correct, fully fixture-tested geometric math and vessel-modeling primitives that every later layer depends on — zero framework dependencies, so the same code runs in the browser and on the server.
**Depends on**: Nothing (first phase)
**Plans**: 3 plans

Plans:
- [x] 01-01: Project toolchain, shared Result<T> degenerate-case union, Vessel/Position Zod value objects
- [x] 01-02: bearing() and relativeBearing() geometry functions with fixture suite
- [x] 01-03: cpa()/tcpa() vector math and compass/math angle-convert utilities

**Details:** Stood up the npm/TypeScript/Vitest toolchain from scratch; hand-derived trigonometry fixtures covering all four encounter shapes (head-on, crossing, overtaking, reciprocal-heading-off-axis) plus exact-boundary and degenerate-input cases, all via TDD RED/GREEN cycles.

### Phase 2: COLREGS Rules Engine

**Goal**: Given any two-vessel scenario, the system correctly classifies the encounter and determines give-way/stand-on with a transparent reasoning trail — the project's core value — validated against textbook fixtures before any UI exists.
**Depends on**: Phase 1
**Plans**: 2 plans

Plans:
- [x] 02-01: Domain types + isolated Rule 7 risk gate and Rule 18 priority-tier primitives
- [x] 02-02: classifyEncounter() dispatch (Rules 7/13/14/15/18) with reasoning trail and full fixture suite

**Details:** The Rule 7→13→14→15→18 sequential dispatch with inline reasoning-trail accumulation, sticky-overtaking hysteresis, and inclusive ±5° doubt bands, verified against a 16-fixture hand-derived suite. A code-review pass caught and fixed an initial implementation that applied Rule 18 uniformly to crossing AND overtaking — Rule 13(a) explicitly overrides Rules 4-18, so this would have produced a legally incorrect give-way verdict.

### Phase 3: Persistence & API Layer

**Goal**: Scenarios can be durably persisted and retrieved through a clean application/API boundary that always re-derives the verdict from stored inputs and never trusts a stored result.
**Depends on**: Phase 2
**Plans**: 3 plans

Plans:
- [x] 03-01: Docker Postgres, Prisma schema/config, initial migration, PrismaClient singleton
- [x] 03-02: Scenario repository + application-layer re-derive-on-read service
- [x] 03-03: scenario/gallery tRPC routers, route handler, end-to-end integration tests

**Details:** A thin Prisma repository (create/findByShareId/findCurated) plus an application-layer service that is the sole place `classifyEncounter()` runs, wiring the "always re-derive on read" guarantee end-to-end — proven via a `createCallerFactory` integration test across the full router → service → repository → domain chain.

### Phase 4: Interactive Chart Sandbox

**Goal**: Users can interactively set up a two-vessel encounter on a chart and see live, visually-explained classification as they drag — the main interaction loop and demo centerpiece.
**Depends on**: Phase 2
**Plans**: 6 plans

Plans:
- [x] 04-01: Tailwind v4 + RTL/jsdom environment, Next.js App Router scaffolding, shared sandbox prop contracts
- [x] 04-02: resolveDoubtGeometry() pure domain helper (TDD)
- [x] 04-03: ChartPanel (SVG rendering + hull/rotate-handle drag hooks)
- [x] 04-04: ControlPanel (speed + vessel-type form controls)
- [x] 04-05: ReasoningPanel (verdict banner, full trail, doubt caveat)
- [x] 04-06: SandboxContainer wiring + app/page.tsx

**Details:** SVG chart rendering both vessels (role-colored hulls + GW/SO/MUTUAL badges, relative-bearing line, overtaking-boundary cones) with native Pointer-Events hull-drag and rotate-handle-drag hooks wired directly onto SVG hit-targets. Live human UAT found dragging/rotating "tricky" across two rounds of fixes — root cause was invisible hit-shapes not matching what the user visually saw; fixed by attaching pointer handlers directly to the visible, solid-filled shape itself. This was the first end-to-end demoable phase.

### Phase 5: Save, Share & Gallery

**Goal**: Users can save and share a scenario via link and browse a curated gallery page of classic textbook encounters, both reusing the persistence layer and sandbox UI already built.
**Depends on**: Phase 3, Phase 4
**Plans**: 5 plans

Plans:
- [x] 05-01: tRPC client provider + server-side caller wiring
- [x] 05-02: Curated seed data (6 scenarios) + Prisma seed script
- [x] 05-03: SandboxContainer initialScenario/banner props + Save flow
- [x] 05-04: /gallery listing page
- [x] 05-05: /s/[shareId] detail page, Copy Link, end-to-end human verification

**Details:** Users can save a scenario (redirects to `/s/[shareId]`), share that link, and browse a curated gallery of 6 textbook encounters, each linking into the same detail route. The final human-verify checkpoint (the first time anyone actually ran `npm run dev` to completion) surfaced and fixed a real, previously-undiscovered bug: neither Turbopack nor Next's default webpack resolves this codebase's `.js`-suffix-pointing-at-`.ts` import convention (established Phase 1, ~98 imports/37 files) — fixed via webpack + `resolve.extensionAlias`, user's choice over a project-wide import rewrite.

## Milestone Summary

**Key Decisions:**
- Horizontal-layers build order (domain → persistence → UI → save/share) to validate the riskiest logic (COLREGS classification) before any UI/persistence complexity sat on top of it
- SVG + native Pointer Events over react-konva/canvas — 2-vessel scale doesn't justify canvas, and SVG gives free RTL-testable DOM nodes
- Hand-rolled flat-plane geometry over geolib/turf.js — synthetic chart-sandbox positions, not real geodesy; the math is the portfolio's core value
- Plain TypeScript + Zod domain layer over json-rules-engine/xstate — COLREGS 11-18 is fixed published law, not runtime-editable rules or a time-based state machine
- Scenarios saveable/shareable via link, no auth — exercises the full backend stack while keeping scope minimal
- `next dev`/`next build` run via webpack (not Turbopack) with `resolve.extensionAlias`, to preserve the established `.js`-suffix import convention without a 37-file rewrite

**Issues Resolved:**
- Rule 18 incorrectly overriding Rule 13 overtaking verdicts (Phase 2, caught in code review)
- SVG drag/rotate hit-targets not matching visible shapes (Phase 4, live human UAT)
- Codebase-wide dev-server module-resolution gap silently present since Phase 1, only surfaced by Phase 5's live end-to-end verification
- Local Postgres port collisions with unrelated projects on the same host (Phase 5 wrap-up), resolved via a gitignored `docker-compose.override.yml` remapping to port 5433

**Issues Deferred:**
- Gallery page placement — currently its own `/gallery` route; user wants it embedded on the home page below the sandbox instead (captured as a todo, not a v1.0 gap)
- Non-blocking Phase 4 code-review findings (e.g., `ChartPanel` not visually flagging degenerate/coincident-position case, silent revert on invalid speed input)

**Technical Debt Incurred:**
- None blocking; the gallery-placement redesign above is the only known outstanding UX change
