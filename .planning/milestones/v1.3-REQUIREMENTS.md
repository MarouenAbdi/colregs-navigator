## v1.3 Requirements

Requirements for the CI/CD & Deployment milestone. Each maps to roadmap phases.

### CI (Continuous Integration)

- [x] **CI-01**: GitHub Actions runs lint, typecheck, test, and build on every pull request and on push to main
- [x] **CI-02**: CI test job runs against a real Postgres instance (reusing the existing `docker-compose.yml` config)
- [x] **CI-03**: Prisma client generates automatically on a clean checkout (`postinstall` script) so CI and fresh installs succeed
- [x] **CI-04**: Node.js version is pinned via `.nvmrc`, used consistently by local dev, CI, and the host
- [x] **CI-05**: All four CI checks are required status checks via branch protection on `main` — a red run blocks merge
- [x] **CI-06**: README displays a live CI status badge

### CD (Continuous Deployment)

- [x] **CD-01**: App auto-deploys to production on merge to `main` via the hosting platform's native Git integration
- [x] **CD-02**: Production database migrations run automatically as part of deploy, gated to production builds only, via `prisma migrate deploy`

### HOOKS (Pre-commit Hooks)

- [x] **HOOKS-01**: Husky + lint-staged run ESLint (`--fix`) on staged files at commit time; full typecheck/test suite stay CI-only

### DOCS (Contributor Documentation)

- [x] **DOCS-CONTRIB-01**: `CONTRIBUTING.md` documents setup, running checks locally, real pre-commit hook behavior, branch/commit conventions, PR expectations, and a rollback note

### DEPLOY (Hosting & Database Provisioning)

- [x] **DEPLOY-01**: App is deployed to a hosting platform (Vercel) with a real, publicly-reachable production URL
- [x] **DEPLOY-02**: Production Postgres (Neon) is provisioned and wired to the app
- [x] **DEPLOY-03**: All required environment variables (per `.env.example`) are configured in the host's production environment

### HEALTH (Go-Live Verification)

- [x] **HEALTH-01**: `/api/health` endpoint performs a real DB connectivity check and returns a meaningful status
- [x] **HEALTH-02**: Live deployment is verified end-to-end with a real request (not just a green build log)
- [x] **HEALTH-03**: Live deployment is verified to survive a post-idle-period request (overnight test) — no cold-start/DB-suspend failure
- [x] **HEALTH-04**: A documented rollback procedure exists (host's one-click "promote a previous deployment")

## Out of Scope

Explicitly excluded. Documented to prevent scope creep.

| Feature | Reason |
|---------|--------|
| Staging environment / multi-env promotion pipeline | Disproportionate for a solo-authored portfolio project; a single production environment is the credible scope |
| Kubernetes / Docker orchestration in production | Vercel's managed platform already solves deployment; container orchestration solves a scale problem this project doesn't have |
| Blue-green / canary / traffic-shifting deploys | No meaningful traffic to shift; adds complexity without a real corresponding risk to mitigate |
| Dedicated secrets-management system (Vault, etc.) | Two secrets total (dev/test DB creds in `docker-compose.yml`, prod `DATABASE_URL` in the host's env store) — a secrets manager solves a problem of scale this project doesn't have |
| Custom observability stack (Grafana/Prometheus) | The health-check endpoint + host's built-in deploy logs are proportional; a dedicated observability stack is overkill for a single-instance portfolio app |
| CI build matrix across Node versions/OSes | Single deploy target, single Node version pinned via `.nvmrc` — a matrix tests compatibility this project doesn't need to guarantee |
| Hand-rolled GitHub Actions deploy step alongside host-native CD | Named anti-pattern from research — running both risks duplicate builds/race conditions; the host's native Git integration already covers CD |
