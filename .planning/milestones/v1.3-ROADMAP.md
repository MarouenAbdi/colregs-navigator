## Overview

A DevOps-competency milestone: a real GitHub Actions CI pipeline (lint, typecheck, test against a live Postgres, build) gates every PR via required branch-protection status checks; Husky + lint-staged pre-commit hooks auto-fix staged files; `CONTRIBUTING.md` documents real (not aspirational) contributor workflow; and the app is deployed to a live, publicly-reachable Vercel production URL backed by a provisioned Neon Postgres database, with an environment-gated `prisma migrate deploy` wired into the build, a `/api/health` DB-connectivity check, and a live-exercised rollback/promote path. Every requirement was verified against real infrastructure (live PRs, live branch protection via `gh api`, a live Vercel deployment, a live external HTTP request, a genuine 8+ hour idle window, and a live rollback/promote cycle against real deployment IDs) — not just green build logs or local simulation.

## Milestone Summary

**Key Decisions:**

- GitHub Actions stays CI-only; CD is the hosting platform's native Git integration, not a 5th Actions deploy job — avoids the "hand-rolled Actions deploy alongside host-native CD" anti-pattern identified in research (Phase 14)
- Resolved the CI-05 branch-protection blocker by making the repo public (over upgrading to GitHub Pro or deferring) — free, unlocks branch protection immediately, fits the project's portfolio/interview purpose; verified no `.env` was ever tracked in history before doing so (Phase 14)
- Migration gate keys off `process.env.VERCEL_ENV === 'production'` exactly, running a single hardcoded `prisma migrate deploy` with zero interpolated input — never `migrate dev`, never `db push` (Phase 14)
- Neon's direct/unpooled connection string is used for `DATABASE_URL` in production (not the pooled one), since `prisma migrate deploy` breaks against PgBouncer-pooled connections (Phase 15)
- Rollback runbook committed via PR review (not a direct push to main), per the user's explicit preference for a PR-review flow on all main-bound changes (Phase 15)

**Issues Resolved:**

- Three real CI bugs surfaced only by exercising `ci.yml` against a live PR (Phase 14, plan 14-02), including a TypeScript-preview build-step failure resolved via Next.js's own `hasNativeTypeScriptPreview()` escape hatch after two narrower workarounds were tried and rejected
- A `set -e` trap in `.husky/pre-commit`: husky wraps hooks in `sh -e`, so `grep`'s exit-1-on-no-match would have aborted the `.env*` guard (and the whole hook) on every normal commit with no staged `.env` files — fixed with `|| true` on both grep stages (Phase 14, plan 14-03)
- A `vercel link` project-name auto-detection bug created a spurious empty Vercel project from the worktree's directory basename instead of linking the real `colregs-navigator` project — caught immediately by cross-checking `.vercel/project.json` against `vercel project ls`, fixed by hand-writing the correct `projectId`/`orgId` (Phase 15, plan 15-03)
- Post-audit doc fixes: a stale README.md sentence self-contradicting the live-deployment status, a stale CONTRIBUTING.md Rollback section never superseded after the real rollback path shipped, a missing SUMMARY.md frontmatter block that hid HEALTH-04 from automated extraction, and a missing Phase 15 VERIFICATION.md — all four found and closed inline during the milestone audit (2026-07-22)

**Technical Debt Incurred:**

- CI-02/HEALTH-01: `/api/health` has zero automated CI regression coverage — `vitest.config.ts` only globs `src/**/*.test.{ts,tsx}`, and `app/api/health/route.ts` lives outside `src/`, so the one DB-backed API route this milestone built is invisible to CI. Verified only manually (locally in 15-01, live in 15-03); a future regression would ship silently through a green pipeline.
- A spurious empty Vercel project (`agent-a5473b04789dea3ed`, created by the 15-03 `vercel link` mis-detection bug) was never deleted — `vercel project rm` was blocked by this environment's destructive-action policy. Harmless (no deployments), flagged for the user to remove via the Vercel dashboard at their convenience.
